# caddy-tls-sans-json

A tiny Caddy v2 HTTP handler that reads a native value from Caddy's request replacer, JSON-encodes it, and stores the encoded result as a string in another replacer value.

This is useful when a Caddy placeholder contains a native Go value such as an array, object/map, boolean, or number, but a later handler (for example `request_body`) needs valid JSON text.

## Generic mode

Configure a source and destination:

```json
{
  "handler": "tls_sans_json",
  "source": "http.request.tls.client.san.dns_names",
  "destination": "http.request.tls.client.san.dns_names_json"
}
```

You can then use:

```text
{http.request.tls.client.san.dns_names_json}
```

in handlers that consume placeholders as strings.

`source` and `destination` may be written either as bare replacer keys:

```json
{
  "source": "http.request.tls.client.san.dns_names",
  "destination": "my.json_value"
}
```

or with braces:

```json
{
  "source": "{http.request.tls.client.san.dns_names}",
  "destination": "{my.json_value}"
}
```

The braces are stripped before lookup/storage.

## Conversion examples

The handler uses Go's `encoding/json`, so values are converted to valid JSON text.

| Native source value | Destination string |
| --- | --- |
| `[]string{"one", "two"}` | `["one","two"]` |
| `map[string]any{"enabled": true}` | `{"enabled":true}` |
| `true` | `true` |
| `123` | `123` |
| `"hello"` | `"hello"` |
| `nil` | `null` |

The destination value itself is stored as a string in Caddy's replacer. This means it can be safely embedded into JSON generated by `request_body` without Caddy flattening arrays/maps into Go's default string representation.

## Example with `request_body`

```json
{
  "handler": "tls_sans_json",
  "source": "http.request.tls.client.san.dns_names",
  "destination": "my.sans_json"
},
{
  "handler": "request_body",
  "set": "\\{\"host\":{my.sans_json}}"
}
```

If the native source value is:

```text
[]string{"foo.example.com", "bar.example.com"}
```

the generated request body contains:

```json
{
  "host": ["foo.example.com", "bar.example.com"]
}
```

## Backward-compatible TLS SAN mode

For compatibility with the original version, omitting both `source` and `destination` keeps the old behavior:

```json
{
  "handler": "tls_sans_json"
}
```

This creates:

```text
{http.request.tls.client.san.dns_names_json}
```

containing the leaf client certificate's Common Name first (when present), followed by all DNS SANs.

For example:

```text
CN = client01
DNS SANs = foo.example.com, bar.example.com
```

produces:

```json
["client01","foo.example.com","bar.example.com"]
```

## Build

With `xcaddy` installed:

```bash
xcaddy build v2.11.4 \
  --with github.com/avalitan/caddy-tls-sans-json
```

For an existing custom build, add the same `--with` argument alongside your other modules.

## Notes

- The source must exist in Caddy's request replacer when this handler runs.
- If the source placeholder is unknown, the request fails with an HTTP 500 error.
- If only one of `source` or `destination` is configured, Caddy configuration validation fails.
- The destination is overwritten if it already exists.
